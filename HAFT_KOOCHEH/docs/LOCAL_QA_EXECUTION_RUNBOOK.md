# Runbook اجرای یک‌باره QA محلی — HAFT KOOCHEH

**وضعیت: برنامه‌ریزی/آماده‌سازی؛ هیچ آزمونی با این سند اجرا یا PASS نشده است.**
**هدف: استفاده حداکثری از یک نوبت دسترسی به لپ‌تاپ و گوشی، بدون تغییر سورس بازی.**

این Runbook چهار کار مستقل را در یک جلسه محلی مرتب می‌کند: QA-001B، TEST-11، QA-002 و QA-003.
نتایج باید جداگانه ثبت شوند؛ موفقیت یکی جایگزین دیگری نیست.

## ۱. ترتیب و Gateها

| ترتیب | کار | نیاز سخت‌افزاری | نتیجه مورد انتظار |
| --- | --- | --- | --- |
| 1 | QA-001B: بررسی تعاملی Godot Editor | لپ‌تاپ Desktop | شواهد Editor و Main Scene |

**Gateهای اصلی:**
- مرحله ۱.۴ تا موفقیت سه اجرای مستقل TEST-11 و بررسی مدیر پروژه پذیرفته نیست.
- QA-001B پیش از Vertical Slice باید تعیین تکلیف شود.
- QA-002 پیش از ادعای Android Export موفق لازم است.
- QA-003 تا زمانی که ورودی سخت‌افزاری واقعی آزمایش نشده، NOT RUN می‌ماند.
- مرحله ۱.۵ در این Runbook شروع یا پیاده‌سازی نمی‌شود.

## ۳. QA-001B — بررسی تعاملی Editor

QA-001B قبلاً OPEN مانده است؛ PASS بودن Import یا Headless جای تعامل واقعی Editor را نمی‌گیرد.

1. Godot دقیق 4.7.2 Stable Standard را اجرا کنید و خروجی `--version` و About را ثبت کنید.
2. پروژه را از `HAFT_KOOCHEH/project.godot` باز کنید.
3. FileSystem Dock را باز کنید و فایل `scenes/app/main.tscn` را پیدا کنید.
4. صحنه را باز کنید و وجود درخت `Main / UI / Title` را در Scene Tree تأیید کنید.
5. Label عنوان را در یک کپی جداگانه تغییر دهید؛ Save کنید.
6. صحنه را ببندید، دوباره باز کنید و ماندگاری تغییر را بررسی کنید.
7. تغییر آزمایشی را در کپی دور بریزید؛ نسخه Git پروژه نباید تغییر کند.
8. F6 و F5 را اجرا کنید و تصویر واقعی پنجره، log و Exit Code را ذخیره کنید.
9. اندازه‌های 1280×720، 1600×720 و 1024×768 را بررسی کنید. عنوان نباید بریده شود و مرکز bounding box عنوان باید حداکثر 8 px از مرکز محدوده محتوای 16:9 فاصله داشته باشد.
10. OS، GPU/Driver، Renderer، نمایشگر و هر خطای Editor/Portal/Vulkan را ثبت کنید.

اگر FileSystem، بازکردن صحنه، Scene Tree، Save یا Reopen قابل تأیید نبود، QA-001B همچنان OPEN/FAIL باقی می‌ماند.

## ۴. TEST-11 — آزمون واقعی FPS روی لپ‌تاپ

آزمون فقط با Renderer گرافیکی واقعی و GPU سخت‌افزاری اجرا شود؛ Headless یا Fixed FPS معیار نرخ رندر نیست.

پیش‌نیازها:
- GPU و Driver واقعی شناسایی شوند.
- llvmpipe/Software Rendering رد شود.
- Godot دقیق 4.7.2 Stable Standard باشد.
- Renderer پروژه Compatibility حفظ شود.
- Physics برابر 60 Hz بماند.
- VSync و FPS cap ثبت شوند؛ VSync برای آزمون طبق فرمان آزمون غیرفعال باشد.
- سه اجرای 120 FPS در سه فرایند مستقل انجام شوند.

معیارهای ثابت:
- هدف: 120 FPS
- پذیرش میانگین: `abs(actual_fps - 120) <= 12`
- مدت واقعی: `abs(wall_seconds - 10.0) <= 1.0`
- Physics Tick: دقیقاً 600
- Physics Rate: دقیقاً 60 Hz
- Coin: دقیقاً 3
- Score: دقیقاً 30
- Exit Code: صفر
- هر سه اجرای مستقل باید PASS شوند.

آستانه، مدت، تعداد Tick، ترتیب ورودی، Assertion یا منطق بازی تغییر نکند.
نتیجه 30/60 FPS، نتیجه 120 FPS را جایگزین نمی‌کند.

برای هر اجرا Actual/Min/Max FPS، Frame Time، Wall Time، Frames، Tick، Coin، Score، Exit Code، GPU، Driver، Display Refresh، VSync و مسیر لاگ ثبت شود.

## ۵. QA-002 — Android Debug Export و نصب

پیش‌نیازهای مورد توافق در QA:
- OpenJDK 17
- Android Platform Tools نسخه 35 یا بالاتر
- Build Tools 35.0.1
- Android Platform 35
- Command-line Tools latest
- NDK 28.1.13356709 (r28b)
- CMake 3.10.2.4988404
- Godot Export Templates دقیق 4.7.2.stable

اگر Workflow اندروید CI اصلاح و تأیید شد، Artifact مربوط به Branch مرحله ۱.۴ را دریافت کنید؛ Artifact نسخه ۱.۳ را به‌جای APK مرحله ۱.۴ استفاده نکنید.

اگر Export محلی انجام شد:
1. مسیرها، نسخه‌ها، `source.properties` و تنظیمات Editor را ثبت کنید.
2. فقط Debug APK بسازید؛ Release Key لازم نیست.
3. APK را با CRC/ZIP و SHA-256 بررسی کنید.
4. APK را روی دستگاه واقعی نصب کنید.
5. نصب، اجرا، جهت Landscape، نمایش عنوان/Prototype، خروج و بازگشایی را ثبت کنید.
6. Logcat و خطاهای Parse/Resource/Runtime را ذخیره کنید.

ساخت APK در CI به‌تنهایی QA-002 را کامل نمی‌کند؛ نصب و اجرای دستگاه واقعی لازم است.

## ۶. QA-003 — لمس سخت‌افزاری واقعی

دستگاه هدف در صورت دسترسی: Samsung Galaxy A16 4G؛ اگر دستگاه دیگری استفاده شد، مدل و نسخه Android دقیق ثبت شود.

روی Prototype مرحله ۱.۴ و با Touch واقعی موارد زیر بررسی شوند:
1. لمس کوتاه در فضای بازی یک درخواست پرش ایجاد کند.
2. نگه‌داشتن لمس، ارتفاع پرش را افزایش ندهد.
3. لمس دوم هنگام حضور در هوا Double Jump ایجاد نکند.
4. لمس هم‌زمان انگشت دوم ورودی پرش اضافه نسازد.
5. Drag/Move انگشت، پرش تکراری ایجاد نکند.
6. Release ورودی را به‌درستی پایان دهد.
7. لمس کنترل UI یا منو، پرش تولید نکند.
8. پس از شکست، ورودی دیررس Player مرده را فعال نکند.
9. پس از Restart، تلاش تازه و کنترل لمسی سالم باشد.
10. پس از رفتن برنامه به Background و بازگشت، ورودی گیرکرده یا پرش خودکار رخ ندهد.

از صفحه، ویدئو/تصویر، logcat و در صورت امکان شمارنده رویدادها شواهد بگیرید.
در اسناد فعلی آستانه عددی برای Touch Latency تعیین نشده است؛ مقدار مشاهده‌شده را اندازه بگیرید و گزارش کنید، اما حد پذیرش جدید اختراع نکنید.
